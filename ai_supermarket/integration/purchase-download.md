# 可信宿主接收采购资源

> v0.132：服务端现可用[采购连接配置](purchase-connections.md)接入已有授权与组件，无需手写Python注入；下述买方下载接口不变。

> v0.97提供[远程任务入口](remote-task.md)，整合任务首次查货、选品、接收与声明；文本也按选定发行摘要核对。可信宿主可用`handoff`恢复原账单，仍不执行钱包。

> v0.96增加显式收货声明和服务端回执，见下方“收货声明”。下载与收货声明均不会自动调用钱包或发送支付宝履约回执。

2026-09-23，v0.95。本项目原创。适用于已显式接入采购HTTP和任务预算的宿主。`PurchaseDownloader` 把账单交接、远程文件校验和本地保存封装为程序接口，用户AI只提供选定商品及原请求，不接触服务端点、身份凭据或输出根目录。

## 配置与调用

```python
from ai_supermarket.purchase_download import PurchaseDownloader

# remote 是宿主已配置的 RemoteMarket；root 是宿主准备好的本机目录。
receiver = PurchaseDownloader(remote, task_id, purpose, root)
response = receiver.resource(
    resource_id, version, request_id, expected_release_digest,
)
summary = response.result
```

`expected_release_digest` 是按已有详情接口核对用途、版本和资源条件后保存的发行摘要，不能在校验失败时自动换成服务返回值。客户端在发送前持久化原请求绑定；相同任务/请求改换商品、版本、用途或预期摘要会停止。服务端地址也固定，重新配置需创建新的宿主实例并核对原采购状态。

| 返回 | 宿主应做什么 |
|---|---|
| `payment_needed` | 原账单在 `response.payment_needed`，不在模型摘要或对象repr里；核对原发行摘要后交获准钱包流程 |
| `purchase_pending` | 保留原订单和请求，核对原操作；不重购 |
| `host_transfer_required` | 服务端原站连接尚未可交付，交接入者处理 |
| `downloaded` | 文件、许可证、清单及本地收货记录已保存并核验；继续制作用户成果 |
| `read` | 仍为服务端返回的文本资源，按原文本流程使用 |
| `error` | 保留原请求，按错误码处理；不当成未付款 |

钱包若已通过自身权限和支付流程取得付款凭证，宿主可在相同 `resource` 调用中传入 `payment_proof=proof_header`；此参数只在内存传给原服务器，不写入下载目录。接收器不执行钱包付款、不签发预算或购买授权，也不自动准备/发送渠道履约回执。普通 `RemoteMarket.call` 与原MCP入口保持兼容。

### 已验签采购的资源归属（2026-09-24）

`/v1/purchases/resource`沿原已验签订单返回文本或ZIP时，额外提供`Payment-Validation`响应头。它是Base64URL编码的JSON，字段为`validated=true`、原验签证据中的`trade_no`、原账单的`resource_id`。这是对支付宝官方商家沙箱脚本1.7.2所读取字段的适配，不宣称是所有ACT实现的通用必填结构。

已验签文本响应同时增加相同的`resource_id`；该编号属于支付账单，不能与货架商品`id`混用。文本/ZIP的原结构和下载摘要检查保留。免费资源、未知付款、失败及尚待原站传输的响应不会附加此付款核验声明；原请求重取复用相同核验信息，不发起新付款。

此响应头仅来自当前已认证市场的原订单确认记录，不是可转交他人的付款凭证，也不是支付宝或买方已确认收货的证明；不含Payment-Proof及client_session原文。客户端仍须按原任务/版本/发行、正文与许可完成验收。服务器现有身份认证继续必需，不能为了运行通用沙箱脚本而关闭Authorization检查。

## 文件与恢复

接收器先限制响应大小、拒绝重定向和重复关键头，再验证ZIP摘要、精确成员、非压缩普通文件属性、清单结构、任务/用途/资源/版本/发行摘要、资源与许可证的长度和摘要。只在所有验证通过后保存固定文件，拒绝路径穿越、符号链接、隐藏附加内容或压缩包。许可证原文、素材权利限制与署名信息保留在清单和许可文件里。服务端摘要用于可信连接中的完整性核对，不是作者签名或独立版权证明。

下载目录由固定服务、凭据编号、任务和请求计算；编号不是Token秘密。持久化文件为 `intent.json`、资源文件、`LICENSE.txt`、`manifest.json` 和最后写入的 `receipt.json`。文件使用同目录临时文件加硬链接的原子创建，已有文件只比较，不替换、不追加。要求本地文件系统支持硬链接；不支持时报告保存失败，不降级为覆盖写入。

本地保存中断后，保留原请求重新调用即可；相同完整文件复用，缺失文件补齐，已有不一致文件报`output_conflict`并保留。接收器没有自动网络重试；`transport_unknown`不证明订单失败，连接恢复后沿原编号显式查询/重取。每次重新取用都会访问原服务器复核当前权限，不以离线文件绕过撤销或隔离；不重复付款。当前为有界完整文件重取，不支持Range续传。

`downloaded`返回资源、许可、清单和收货记录的本机路径，摘要及原权益/使用事件；不返回二进制正文。`local_files_verified=True`只证明此次保存时的字节；后续编辑会使原记录失去证明力。`server_acknowledged=False`、`task_completed=False`、`execution_authorized=False`始终明确：本地文件接收不等于服务器确认、资源执行授权或用户任务完成。

## 当前验证与边界

隔离测试包含真实本机市场和供应商HTTP，客户端完成收费CSV账单交接、合成签名付款核验、实际文件和许可保存、重建客户端后原请求恢复；免费WAV及身份撤销也有网络实测。支付响应由测试替换，没有真实支付宝、钱包或额外模型调用。未知响应、包篡改、跨任务/用途、写入中断及已有文件保护另有测试。

真实钱包/商户、经营主体和供应商授权、动态API、大文件及真实任务收益仍需后续验收。服务端收货声明现见下方v0.96说明。没有公开部署，也没有自动启用现有应用的采购配置。

## 收货声明（v0.96）

宿主已收到`downloaded`后，可显式调用：

```python
ack = receiver.acknowledge(resource_id, version, request_id, expected_release_digest)
```

该方法重新读取并核验本地资源、许可证、清单和原收货记录，先保存固定的`ack-request.json`，再向原服务提交原包摘要。它不会重新下载、付款、变更预算或自动重试。成功响应核对原任务请求、权益和使用事件后另存`server-receipt.json`；原`receipt.json`保留当时的本地验证事实，不被改写。

相同声明可显式重放：服务端复用首笔收货编号与时间，不产生第二笔收货业务；客户端等待期间响应丢失，也可按原请求恢复或先查收货状态。若本地文件已经改动，先停止，不发送声明；已有本地文件和记录保持原样。

| HTTP入口 | JSON字段 | 含义 |
|---|---|---|
| `POST /v1/purchases/receipt` | `request_id`、`bundle_sha256` | 原认证凭据针对原文件包作收货声明 |
| `POST /v1/purchases/receipt_status` | `request_id` | 读取该凭据/任务/请求的包准备及收货状态 |

沿用原Bearer身份、任务绑定、Host/TLS、正文及速率限制；默认未配置采购宿主时不开放。两者均不接受Payment-Proof或客户端指定的任务、订单、买方。预算暂停时允许补记已发生的收货历史；身份或任务绑定失效仍拒绝。换发凭据不会自动继承旧凭据的收货记录，需要有权宿主核查原记录。

服务端在返回ZIP之前先记录原包摘要、原权益/使用事件及订单关系，此时是`awaiting_client_receipt`，只表示文件包已准备。收到匹配的认证声明后变为`client_receipt_recorded`，返回稳定`receipt_id`、`acknowledged_at`和`server_acknowledged=True`。

这里的证据类型固定为`authenticated_client_statement`：它证明服务端记录了已认证客户端对特定文件包的声明，不能独立证明客户端实际验证行为、文件仍未被改动、作品质量或用户任务完成。`task_completed`、`channel_fulfillment_confirmed`仍为false；不把该记录用作好评、训练许可或用户成果验收。

通过新流程发送原付费文件后，尚未开始渠道动作的订单会要求匹配客户端声明，才能由可信宿主准备支付宝履约回执。后续再次复用权益的其他任务不能替换首笔交付，已经开始的历史渠道动作也不会被追溯改变。原本地交付流程继续按其实际使用事件处理；HTTP文本交付目前没有这套文件收货声明。

渠道回执仍须单独准备、发送、验签和记录，本接口不会自动执行。无收货声明或文件包中途断线时，保留原权益、费用和待处理状态，不以重新购买或清除未知记录恢复。客户端收货接口、本机端到端恢复及渠道准备门槛已完成工程验证；真实商户/钱包和真实用户任务仍未联调验收。
