# 就绪检查、联合快照与恢复

来源：本项目原创。就绪检查判断服务依赖能否读取；恢复工具把既有状态复制到新目录，经过核对才开放。两者都不是生产认证或付款授权。

## 当前范围

v0.134补齐原请求定位：副本已放行，并由有权人完成新凭据、任务预算复核和新购买委托配置后，同一买方/预算根/任务的旧request_id可找到原采购。已付款且已授予的正文权益沿当前商品、用途与访问规则复用。旧凭据、暂停预算和商品隔离仍阻止取用；不重绑旧委托或放开权限。

未完成、付款未知或尚未授予权益的原请求返回202及原order_id、order_status和host_reconcile_restored_purchase，预算占用保持。status和handoff不重发旧账单，Payment-Proof不触发旧渠道核验。换商品冲突、历史请求歧义会停止。原底层pending_payment保护已经能阻止重复下单；本轮补的是可查询原订单的恢复状态。未决订单的真实核对、结算和恢复执行仍待完成；外部文件、API与供应商账本并未因此全部恢复。

v0.131：在原订单、支付、退款、账单/预算与采购宿主校验之上，接续客户端文件包/收货声明、远程文件交付标记、原订单收货指针及渠道履约记录。按原权益、使用事件、发行、资源/许可证摘要重建清单核对；客户端声明仍不证明任务完成。跨身份与预算库核对原凭据归属和任务存在，撤销或过期凭据仅作为历史，不重新启用。

有采购委托或账单记录时，ready必须同时提供原预算库。快照、快照核验、恢复完成和放行均核对任务归属、原预算请求、占用编号、金额与支付确认回执。缺失或错误占用不能凭完整市场库通过。暂存账单加已开始预算、市场仍记交接而预算已结算等中断状态保留；生成账单前遗留的占用也不清零。它们仍需核原请求，不能自动重购或重复记费。

渠道记录核对全部尝试与当前状态、固定端点、原交易、付款/交付关联及验签键摘要。未知发送保留待核对；只有原SYSTEM_ERROR历史允许处于显式重试后的待发送状态，本恢复工具不发送、不重试。合成本机测试不能改写成真实确认。退款停止后续访问时，已完成渠道交付的历史查询仍可核对旧收货声明；新收货声明与取用仍受原访问限制。

未登记类型仍拒绝健康或快照，不能删记录或改状态来通过。历史校验不进行新的签名验证，不证明真实资金到账；保留的ZIP摘要和客户端声明也不是独立的远端收货证明。恢复副本仍先隔离、撤销旧凭据并暂停预算。委托中的路径摘要按历史原样保留，不匹配恢复目录上的新宿主授权；本轮不重绑旧采购宿主，也不自动重发账单，恢复后继续采购仍需有权人核对并配置。

独立API次数库、供应商操作库及结果文件也未纳入本联合快照。它不是完整收费/API灾备：运营必须核对原外部账本、在途执行与真实资金状态，不能从市场副本初始化空库接续旧权益。

当前支持开放市场、身份、主子任务预算三个独立SQLite账本，并可加入整任务计量账本。未指定计量时保留格式1三库快照；指定后生成格式2四库快照。开放市场的商品正文与版本已经保存在市场数据库内，因此随快照一起保存。原20项文件目录、邀请账本、凭据原文文件、TLS私钥、部署配置、外部支付/模型服务的真实状态不属于这个快照。

所有源路径必须由受信运营者确认属于同一服务实例；旧部署没有统一实例编号，本工具不能证明任意源文件原本属于同一业务。恢复副本具有统一恢复批次编号，后续混用不同批次会被拒绝。工具没有上传、下载或自动删除行为，不覆盖文件、不自动切换数据库路径。

备份含商品正文、账户信息、凭据摘要、消费及审核记录，需要使用获准访问的受保护目录。校验摘要用于发现内容变化，不证明快照来自可信运营者；应另存可信来源与交接记录。本工具不自动配置Windows目录权限或备份加密，不读取/复制独立凭据文件。

## 进程存活与依赖就绪

| 入口 | 结果 | 证明范围 |
|---|---|---|
| GET /health/live | 200，alive | 进程能响应请求 |
| GET /health/ready | 200，ready；或503，not_ready | 必需数据库存在，结构版本匹配，能读取业务表，恢复门未关闭；已配置账本的恢复批次一致 |

两个入口不要求凭据，仍受Host、来源、TLS与请求频率限制；就绪响应只有一个状态，不显示路径、账号、商品、数量或原始异常。未初始化市场返回not_ready，检查本身不会创建账本。原启动流程仍在首次有效业务调用时建立市场账本；预上线应先初始化/验收业务，再接入流量检查。

若服务使用预算账本，可给HTTP启动器添加`--budget <实际预算账本路径>`，加入就绪检查。省略该参数只检查市场与身份，不能据ready推断预算可用。它不把预算管理暴露给模型，也不自动实施远程费用限制。

使用计量时另加`--measurement <实际计量账本路径>`。四库恢复后的市场记录计量必需标记，省略计量路径、缺库或混用恢复批次均返回not_ready，不创建空库。ready仍不代表历史任务的费用已经逐项复核；单任务证据状态见[计量说明](measurement.md)。

每次探测有短数据库锁等待与SQL执行期限，且受并发/限流约束；不执行全库内容校验或试写业务记录。ready不证明磁盘有足够剩余空间、备份有效、支付可用、商品质量合格、具名人员能接警或生产容量足够。深度完整性、外键、商品内容与许可字段检查在快照和恢复过程中执行。

## 创建和验证快照

以下为命令说明，需要替换为已确认的实际源路径。先安排维护窗口：停止新业务写入入口，等待宿主任务和外部调用收尾；不能仅关闭网页就认为后台任务结束。工具本身不替用户停生产。

```powershell
py -3.12 -m ai_supermarket.recovery snapshot --market work/service/market.sqlite --identities work/service/identities.sqlite --budget work/service/budget.sqlite --output work/backups/snapshot-001
py -3.12 -m ai_supermarket.recovery verify --bundle work/backups/snapshot-001
```

需要保留整任务计量时使用以下四库命令。`--require-measurement`使核验方明确拒绝不含计量的旧格式：

```powershell
py -3.12 -m ai_supermarket.recovery snapshot --market work/service/market.sqlite --identities work/service/identities.sqlite --budget work/service/budget.sqlite --measurement work/service/measurement.sqlite --output work/backups/snapshot-with-meter-001
py -3.12 -m ai_supermarket.recovery verify --bundle work/backups/snapshot-with-meter-001 --require-measurement
py -3.12 -m ai_supermarket.recovery restore --bundle work/backups/snapshot-with-meter-001 --output work/recovery/candidate-with-meter-001 --require-measurement
```

四库模式同时取得四份写入预留锁。缺失、重复源路径、损坏的计量状态或缓存token大于输入token都会拒绝；恢复后的四库市场不能在下次快照中默默遗漏计量。格式1原行为保留，不隐式修改旧账本的表结构。

预算新增微额精度后，两种快照格式都会保存并验证预算spec/meta中的精确金额；缺失、无关联或与分显示矛盾的费用拒绝进入完整快照。详见[预算说明](shared-budget.md)。预算恢复后，市场未放行不能建立新预算或恢复消费，晚到费用仍可登记；保持固定同目录文件名与同一批次，不把预算副本单独移走使用。

目标目录必须尚不存在，包括空目录也拒绝。程序先按固定路径顺序取得全部数据库的写入预留锁，再分别使用SQLite备份接口制作快照；不能只复制主数据库文件而漏掉尚在WAL中的已提交数据。WAL是SQLite保存近期写入的一种日志。新的快照转换为独立文件，不修改源账本的日志模式。

所有写入锁同时持有时，数据库状态对应同一时间段；这不等于三库业务动作天然具备跨库事务，也不能冻结外部支付或模型执行。尚未落到数据库的外部结果必须保留为未决并核原请求。争用、结构不匹配、正文摘要不一致或完整性失败会停止；失败目录保留，不能复用为下一次目标。

manifest.json最后写入，列出固定文件名、字节数、摘要、快照编号及时间。没有清单的目录不算完成。创建开始即写入专用快照标记，市场、身份和预算的业务入口拒绝直接运行该目录中的账本，必须先恢复到新目录。verify拒绝标记/清单不一致、清单外文件路径、符号链接数据库、额外写入日志、摘要不符和结构/内容损坏。断电后的文件与目录持久性仍需实际存储环境演练；看到一个目录或退出码记录不能跳过verify。

## 恢复与隔离

```powershell
py -3.12 -m ai_supermarket.recovery restore --bundle work/backups/snapshot-001 --output work/recovery/candidate-001
```

恢复只向新目录执行，不修改源快照或当前服务路径。输出为restored_quarantined，意思是“副本已恢复，但仍隔离”。具体措施：

1. 市场进入pending恢复状态，各次业务调用都会检查；已创建的市场对象也不能绕过。恢复中途失败或缺完成记录不能放行。
2. 副本中原有凭据全部撤销。旧快照可能早于后续撤权事件，不能让旧钥匙重新获得访问。账号既有disabled状态保留；账户资料核对后，由获准运营者另发新钥匙，不自动重新启用禁用账号。
3. 原active预算转paused，原closed状态不变；已发生费用、reserved/in_flight/unknown、回执、父子关系和任务关闭状态保留。未知费用不会变成0，恢复不会自动重做外部请求。
   若启用[同账本总预算](shared-budget.md)，配置、归属方限额及修订审计一同校验并保留；恢复追加一条审计，总预算active转paused，closed不重开。市场放行后仍须先核准总预算，再逐根预算启用，不能清掉未知预留恢复额度。
4. 所有副本写入同一恢复编号，完成记录最后写入。恢复不保证备份时间之后的订单、撤权、商品暂停和费用已经包含；必须向可信记录及供应商查询差异。
5. 含计量时，原任务、调用、费用及验收记录保留，所有历史任务重新进入待复核状态。旧任务不能通过begin/observe重做外部调用；遗漏调用只能据原始证据补录。四库副本须保留同目录固定文件名：计量启动还会核对同目录market.sqlite的放行状态和批次，防止部分放行提前执行新任务。

收到失败结果时保留失败目标作检查，用新的目录重试。不要把缺失账本重新初始化成空库，不以清空未知预留使测试通过，不并行启用旧库和恢复库承接同一业务。

## 运营核对与放行

放行是受信本地管理命令，不是HTTP、MCP或模型工具。真实服务使用前必须完成以下四类核对，保存非秘密的证据编号：

| evidence字段 | 核对内容 | 建议责任人 |
|---|---|---|
| access_review | 备份后新增撤权、账号禁用、权限变化；关闭旧实例和旧凭据的实际路径 | 运营与安全 |
| financial_reconciliation | 原请求对应真实账单；未知费用、晚到结果和未决预留已登记，未决仍占额度 | 财务与技术 |
| delivery_review | 已取得权益、商品风险暂停、版本内容、反馈历史及未交付订单 | 运营与质量 |
| approval | 有权人确认此次恢复范围、未决差异和切换窗口 | 业务负责人 |
| measurement_reconciliation（仅四库必填） | 全任务计量的覆盖、遗漏调用和晚到用量核对范围；未核实任务保持不可比较 | 技术、质量与财务 |

证据文件在三库时恰含原四个字段，四库时另含measurement_reconciliation，值均为字符串。字段值使用真实记录编号，不能填“测试通过”冒充业务核对。程序检查字段和账本批次并把引用写入恢复审计；它不能代替专业人员核验引用内容。全库放行不自动授予历史任务的成本比较资格，仍须逐任务复核。

```powershell
py -3.12 -m ai_supermarket.recovery release --bundle work/recovery/candidate-001 --evidence work/recovery/approved-review.json
```

released开放这份市场副本，并在四库模式开放新计量任务。旧凭据不会恢复，预算不会自动恢复active，服务配置不会自动切换。切换须由运营者保持旧写入入口关闭，依据真实批准使用同一批次全部账本、另发获准凭据、重新核对需要启用的预算，运行端到端样例及就绪检查后才逐步接流量。若已经在恢复库产生新写入，不能直接指回旧库，应停写、保存两侧状态并核对差异。

启用[远程任务预算绑定](task-budget-gateway.md)时，快照会保存并校验绑定元信息。恢复保留原绑定作为历史，但旧凭据被撤销，身份文件位置也参与绑定匹配；运营须在放行和预算复核后签发新凭据并绑定获准任务。不能修改旧记录来复活授权，查询历史不代表当前可执行。

本机文件权限仍是边界。有权直接编辑数据库的人可以修改元信息；这些恢复门不能替代操作系统权限、审计留存及生产签核。本轮没有执行任何真实服务放行或生产切换。

恢复副本必须使用包含本模块和恢复门的已核对程序版本。旧程序可能不认识新增的恢复元信息，不能通过退回旧程序绕过隔离；回退时保持入口关闭并核对数据差异。本工具不更改表结构或隐式升级原账本，只在新恢复副本增加恢复元信息与审计记录。

## 验收与依据

新增[独立服务进程演练](process-recovery-drill.md)：覆盖真实网络请求在业务落库后崩溃、原编号恢复，以及入驻→交付→四库恢复→新凭据与预算复核→原权益取回的组合链路。仅临时数据，不代替真实接手人或生产存储验收。

运行`py -3.12 -m unittest ai_supermarket.tests.test_recovery -v`验证本地完整链路；带网络依赖的环境运行完整测试，额外验证真实HTTP的ready/not_ready、恢复门及live仍存活。

四库与单任务复核另运行`python -m unittest ai_supermarket.tests.test_measurement_recovery -v`，覆盖遗漏回执、中断调用、复核撤回、部分放行、源覆盖声明保留、二次恢复重新隔离以及独立进程管理命令。它们使用合成数据，不证明真实账单已核验。

重点检查正常快照、WAL提交、三库锁同时持有、忙锁、缺库、错误结构、正文篡改、清单路径、未完成副本、不同批次混用、旧凭据失效、旧权益幂等复用、未知费用和关闭状态保持。幂等表示重复同一请求不会产生新的业务副作用。软件演练数据不构成真实财务/内容权利验收。

参考[SQLite备份接口](https://www.sqlite.org/backup.html)、[SQLite事务语义](https://www.sqlite.org/lang_transaction.html)和[Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html)，2026-09-15核对。实现、测试和文档为原创，仅使用既有Python标准库，没有新增依赖；未复制第三方代码。全生命周期状态和实际运营责任见[主计划](../../docs/ai-supermarket-master-plan.md)。
