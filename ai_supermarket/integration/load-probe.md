# 本机负载测量与容量边界

来源：本项目原创。此工具从完整开发源码运行，用于L05-03、L06-01、L07-01/02的工程证据准备。它创建临时合成商品和身份，启动自身的127.0.0.1服务，结束后停止自身进程并清理临时数据；不访问已有市场、不接受外部目标地址、不调用模型或付款，不执行公开部署。

## 如何运行

使用已经安装并核实的Python和项目HTTP依赖，从完整源码根目录执行；work目录须存在，输出文件须不存在：

```powershell
python -B tools/market_load.py --output work/load-search.json --catalog-size 20 --workers 1 --samples 64 --workload search
python -B tools/market_load.py --output work/load-journey.json --catalog-size 20 --workers 8 --samples 16 --workload journey
```

不要把任意报告路径当成运行实例路径。工具没有数据库、URL、凭据或部署配置参数，不会向已有生产实例施加负载。输出存在则在启动负载前拒绝覆盖。运行失败返回非零退出码，保留已创建输出；空文件或failed/error不算有效测量，不能盲目重跑覆盖证据。

本工具是开发验收材料，不在65文件内部运行包的固定清单中。v0.28包仍保留原摘要；后续运行实现改变时重新生成独立候选包。测量必须注明运行源码与环境，不能把其他机器或后续实现的结果归给旧包。

## 固定边界和实际工作量

| 项目 | 当前范围 |
|---|---|
| 目录 | 1～200项原创合成静态资料；内容重复且固定，不代表真实供给分布 |
| workers | 1、4或8个并行客户端工作线程；服务器仍使用真实启动器、单进程和默认限制 |
| search | 最多96个测量样本，每个样本一次真实HTTP搜索 |
| journey | 最多16个工程流程，每流程搜索→查看条件→获取→读取→反馈，共5次请求；程序固定选择样例，不声称AI自主选择已验证 |
| 数据 | 每次新建临时市场和合成买方；价格0、个人内部用途，评价为unknown/not_run |
| 时间 | 请求等待最多3秒；120秒新动作截止时间，启动/收尾仍有额外开销，不承诺精确墙钟硬上限 |
| 重试 | 自动重试0次；当前流程遇到失败停止后续动作，保留失败及实际账本计数 |
| 限制 | 应用并发16、服务启动器连接/任务上限32、每来源IP每60秒120次等原默认值；没有为了提高测量成绩调大限制 |
| 可选能力 | 未启用任务预算强制绑定、邀请或计量库；这份结果不覆盖这些额外路径的容量 |

每个场景先执行3次搜索预热，单独记录、不计入测量延迟。预热不等于搜索缓存命中。就绪探测也消耗默认请求配额；不能只计算业务请求。新场景使用新进程，因此限流窗口重新开始，这不是生产长期运行方式。

## 报告如何解释

P95是按耗时从小到大排列后，至少95%的样本不超过的值；当前采用向上取整的序号算法。只有16个流程时P95就是最大值，样本很小，不能据此推断稳定的长期P95。

- `latency`统计每个样本从开始执行至完成/失败的时间，包含样本内全部请求；`per_tool_latency`分别记录各接口耗时。失败请求仍留在测量中，不只挑成功快请求。
- 这是固定并发、做完一个再做下一个的闭环负载；未统计在线程池中尚未开始的排队时间，也没有模拟独立持续到达的真实流量。`observed_completed_jobs_per_second`只是本次短窗口的实际完成速度，不是最大吞吐或可销售服务承诺。
- `http_status_counts`和`business_status_counts`分别保留网络响应与业务结果。HTTP 200本身不算成功：搜索需找到预置资源，正文需精确一致，反馈需对应使用事件。
- 工程流程结束后核获取、使用、反馈条数以及SQLite完整性和关联关系；反馈仍须是未知/未检查。错误或部分成功不能变成商品好评。
- 报告包含源码摘要、Python/SQLite/Uvicorn版本、系统类型、样本配置、原始耗时和默认限额；不包含凭据、商品正文、账号私密数据或原始异常。响应字节数不是token。
- `observed`表示该受限场景的请求与落库符合预期，不代表达到延迟门槛、生产认证或商业质量；`production_approved`始终false。

报告格式`market-local-load-2`增加独立的`database_integrity_valid`、`foreign_keys_valid`及`request_records_consistent`。`ledger_valid`继续要求全部预期记录齐全，因此false可能仅表示某个流程未走完，不能单独诊断为数据库损坏。每条合成流程按原主体、获取请求编号、使用请求编号关联实际记录，并核回执摘要、资源版本、正文摘要及反馈来源。`record_without_valid_response`表示已找到写入但客户端没有有效回执；`no_record_after_stop`只表示停止本次临时服务后的只读快照中没有记录。两者都不会触发重试或改写原完成率。正文超时即使已收到HTTP 200，也保留结果未知；`phase`、`failure_kind`与收到响应头的耗时帮助区分发生阶段，不输出原始异常和正文。

该核验仅访问探测器自己创建的临时账本，不提供生产账户查询或自动恢复接口。服务停止可能中止仍在进行的合成请求，快照不是对存活的生产请求或外部付款结果的证明；运行容量与正式恢复仍须单独验收。

默认来源IP限额120次/分钟，会约束同一来源的所有买方。仅作算术上界：一个完整工程流程需要5次调用，即使没有任何其他请求，同来源每分钟也不超过24个这类流程；实际还受就绪、工具发现、失败、其他请求和更严格限制影响。不能以短时几十次请求/秒宣传可持续容量，代理后来源识别和共享IP影响也要在获准真实环境核验。

## 上线仍需要什么

本机客户端和服务争用同一台电脑，其他进程、存储和系统调度未隔离；慢请求原因必须进一步定位，不能直接归因于网络、数据库或防护软件。本工具不测公网/TLS、长期历史账本、任务预算模式、恢复期间负载、磁盘耗尽、持续过载或模型/支付延迟。

发布前由技术/测试/运营负责人明确目标流量、商品体积与数量、使用和搜索比例、身份分布、历史账本规模、成本、延迟与错误门槛，再在匹配运行环境测稳定时段、峰值和恢复。出现未知写入、错误正文、账本不一致或持续超时，停止放量，先核原请求和原数据；不要通过放宽权限、丢弃失败记录或取消预算来获得更好的数字。

已有负载观察及尚未完成的验收以[主计划第42节](../../docs/ai-supermarket-master-plan.md#42-本机负载观察与容量边界v029)为准；24份记录含失败，不代表三轮完整发布检查通过，也不构成商业上线批准。
